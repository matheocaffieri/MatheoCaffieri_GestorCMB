1. Introducción técnica

GestorCMB es un sistema de escritorio para la gestión integral de obras de construcción civil. Cubre el ciclo: alta de clientes y proveedores, creación de proyectos, asignación de empleados y materiales por obra, control de inventario, detección de materiales faltantes, generación de informes de compra (con historial de soft-delete), cálculo del monto total del proyecto con márgenes parametrizables y análisis gráfico de costos.

La aplicación está construida sobre .NET Framework 4.7.2 en C# con interfaz WinForms y persistencia en SQL Server (instancia SQLEXPRESS local con autenticación integrada). Se separa en tres bases de datos independientes: GestorCMB para los datos del negocio (mapeado por EDMX), GestorCMB_Users para usuarios, roles, permisos y parámetros, y GestorCMB_Logs para la bitácora técnica.

La arquitectura es en seis capas con dependencias unidireccionales: UI → BL → DAL → DomainModel, con Interfaces como contratos compartidos y Services como anillo transversal (logging, idioma, seguridad, snapshot histórico, hash de contraseñas).

El módulo de Seguridad (árbol Composite de roles y permisos, enum TipoPermiso, hash BCrypt con compatibilidad SHA-256 legacy, recuperación de contraseña por OTP vía SMTP, rol Administrador protegido) está inspirado en patrones reutilizables de cátedra y adaptado al dominio de GestorCMB.

2. Requisitos del entorno de desarrollo

Herramientas

  • Visual Studio 2019 / 2022 con cargas de trabajo .NET Desktop.
  • .NET Framework 4.7.2 Developer Pack.
  • SQL Server Express 2019+ y SSMS para crear las tres bases.
  • MSBuild de Visual Studio (no dotnet build: la solución usa packages.config y se compila con MSBuild clásico).
  • nuget.exe para restauración de paquetes.

Paquetes NuGet relevantes

  • EntityFramework 6.5.1 — ORM para la BD GestorCMB vía EDMX. Referenciado por DAL, BL y la UI.
  • BCrypt.Net-Next 4.0.3 — hash de contraseñas con work factor 12. Referenciado por Services.
  • System.Buffers 4.5.1, System.Memory 4.5.4, System.Numerics.Vectors 4.5.0, System.Runtime.CompilerServices.Unsafe 6.0.0 — dependencias transitivas de EF y BCrypt.

Configuración inicial

  1. Clonar el repo en una ruta sin espacios (p. ej. C:\source\repos\MatheoCaffieri_GestorCMB).
  2. Restaurar paquetes con nuget.exe restore MatheoCaffieri_GestorCMB.sln.
  3. Crear las tres bases en SSMS (por ahora los scripts no están versionados en el repo; ver §9 para la lista de tablas). Nombres: GestorCMB, GestorCMB_Users (también referenciada como CMB_USERS en una connection string legacy), GestorCMB_Logs.
  4. Editar las connection strings en MatheoCaffieri_GestorCMB/App.config. Por defecto apuntan a la instancia local del desarrollador (Data Source=VICTUS-TATE\SQLEXPRESS); reemplazar por .\SQLEXPRESS o el nombre del SQL local de cada máquina.
  5. Configurar SMTP si se quiere probar la recuperación de contraseña: claves SmtpHost, SmtpPort, SmtpUser, SmtpPass en <appSettings>. Ver §10.4.
  6. Compilar el proyecto de UI (MatheoCaffieri_GestorCMB.csproj); arrastra el resto de dependencias.
Seguridad. La SmtpPass en App.config queda en texto plano. En producción debería migrarse a un mecanismo de secretos (App Secrets, variables de entorno, Windows Credential Manager) o, como mínimo, cifrar la sección appSettings con aspnet_regiis -pef. No commitear nunca la contraseña real.
Nota. La autenticación a SQL Server es integrada (Integrated Security=True). El usuario de Windows que ejecuta la app debe tener acceso a las tres bases.

Dos Unit of Work paralelos — no mezclarlos

El sistema convive con dos mecanismos de persistencia distintos en el mismo proceso:

  • SqlUnitOfWork (DAL/FactoryDAL/SqlUnitOfWork.cs): envuelve un GestorCMBEntities de EF y un DbContextTransaction. Lo usan todos los *BL de negocio. Begin/Commit/Rollback/Dispose trabajan sobre la transacción de EF y cierran el contexto en el using.
  • SqlLoginUnitOfWork (DAL/FactoryDAL/SqlLoginUnitOfWork.cs): envuelve un SqlConnection + SqlTransaction directos. Lo usan UsuarioRepository y los repos de AccessDAL/ contra GestorCMB_Users.
Regla. Un BL no abre los dos UoW en el mismo método. Si una operación toca negocio + seguridad, se hace en dos pasos secuenciales con su propia transacción cada una. No hay distributed transaction.

4. Patrones de diseño utilizados

El sistema aplica los siguientes patrones, en orden de importancia para entender el código:

4.1 Singleton

Aplicado a servicios sin estado de negocio que deben tener una única instancia viva durante toda la sesión:

  • BL.LoginBL.SessionManager — singleton thread-safe con doble verificación bloqueada. Expone SessionManager.Instance, Login(Usuario), Logout(), IsLoggedIn(), UsuarioActual y TienePermiso(TipoPermiso). Mantiene el usuario logueado con sus permisos resueltos.
  • Services.Language.LanguageService — singleton público vía la propiedad estática LanguageService.Current. Se inicializa una sola vez en Program.cs con un ILanguageRepository concreto (ResxLanguageRepository) y la CultureCode guardada en Properties.Settings.Default.
  • Services.Logs.LoggerLogic — fachada estática sobre un Lazy<ILoggerStrategy>. No es estrictamente un objeto singleton, pero el comportamiento es equivalente: una sola estrategia viva por proceso, inicializada bajo demanda.

4.2 Factory

  • BL.AccessBL.AccessServicesFactory — fabrica los servicios del módulo de seguridad (AccesoService, RolesService, UsuarioPermisosService, ParametrosService) inyectando los repositorios concretos de DAL/AccessDAL/ a partir de la connection string a GestorCMB_Users.
  • Services.Logs.LoggerFactory — lee App.config["LoggerType"] (file, database, both o lista por comas) y arma la ILoggerStrategy resultante: un único sink o un CompositeLoggerStrategy que reenvía a múltiples.

4.3 Repository

Cada entidad de negocio tiene su interfaz en DomainModel/Interfaces/ (todas implementan la genérica IGenericRepository<T> con Add/Update/Delete/GetById/GetAll) y su implementación EF en DAL/ProjectRepo/. Los repos no abren transacción: reciben el SqlUnitOfWork ya iniciado y operan sobre su Context. Para la BD de seguridad se sigue el mismo patrón pero la implementación es ADO.NET (clase base DALBase en DAL/AccessDAL/).

4.4 Unit of Work

Dos UoW conviven (ver §3): SqlUnitOfWork envuelve EF para GestorCMB y SqlLoginUnitOfWork envuelve ADO.NET para GestorCMB_Users. Ambos implementan Begin/Commit/Rollback/Dispose y se consumen con un using en el BL. 

// Patrón canónico de un BL con UoW
public void Add(Proyecto entity)
{
    if (entity == null) throw new AppException("err_entity_null");

    using (var ctx = new GestorCMBEntities())
    using (var uow = new SqlUnitOfWork(ctx))
    {
        uow.Begin();
        try
        {
            var repo = new ProyectoRepository(uow);
            repo.Add(entity);
            uow.Commit();
            LoggerLogic.Info($"[ProyectoBL] Proyecto agregado. Id={entity.IdProyecto} Desc='{entity.Descripcion}'");
        }
        catch (AppException ex)
        {
            uow.Rollback();
            LoggerLogic.Warn($"[ProyectoBL] Validación al agregar proyecto: {ex.MessageKey}");
            throw;
        }
        catch (Exception ex)
        {
            uow.Rollback();
            LoggerLogic.Error($"[ProyectoBL] Falla al agregar proyecto. Id={entity?.IdProyecto}", ex);
            throw;
        }
    }
}

4.5 Strategy

El subsistema de logging define ILoggerStrategy con tres implementaciones intercambiables:

  • FileLoggerStrategy — escribe archivos diarios en LogDirectory.
  • DatabaseLoggerStrategy — INSERT en la tabla Log de la BD GestorCMB_Logs (connection string LogsConnection).
  • CompositeLoggerStrategy — agrupa varias estrategias (ver §4.6).

4.6 Composite

  • Services.Logs.Strategy.CompositeLoggerStrategy — recibe params ILoggerStrategy[] y delega cada WriteLog a todos sus hijos, capturando errores individuales para que la caída de un sink no rompa los demás.
  • Services.RoleService.RolCompuesto — implementa IPermiso y mantiene una lista interna _hijos. La evaluación TienePermiso(TipoPermiso) recorre recursivamente sus hijos (que pueden ser Acceso u otros RolCompuesto). Es el árbol de permisos del sistema.

4.7 Facade

  • LoggerLogic es la fachada estática que oculta toda la mecánica de Strategy: el resto del sistema solo conoce LoggerLogic.Info / Warn / Error / Critical.
  • LanguageService es la fachada de la i18n: el resto del sistema solo conoce LanguageService.Current?.T("clave").

4.8 DTO / VO

  • DomainModel.Login.UserSession — datos de sesión cargados al loguear.
  • Services.Language.Language — DTO Code + Name para listar idiomas disponibles.
  • Services.LoginService.LoginResult — enum de resultado de login (Ok, CredencialesInvalidas, UsuarioInactivo).
  • DomainModel.Entities.AsignacionMaterialResult — resultado de una asignación de material a un proyecto.

4.9 Exception con clave de mensaje

DomainModel.Exceptions.AppException lleva una propiedad MessageKey: las excepciones del BL no contienen mensajes en español sino claves (err_proyecto_id_required, err_informe_sin_faltantes, etc.) que se traducen en la UI vía LanguageService.Current?.T(appEx.MessageKey). Ver §11.

6. Entidades del dominio

Las entidades de negocio están en DomainModel/Entities/ y se mapean por EDMX contra las tablas homónimas de la BD GestorCMB (ver §9). Las entidades de seguridad están en DomainModel/Login/ y se mapean manualmente desde ADO.NET contra GestorCMB_Users.

Cliente, Proyecto y sus detalles

  • Cliente — destinatario de la obra. PK IdCliente (Guid), NombreContacto, RazonSocial, Mail, Telefono (int), IsActive (baja lógica).
  • Proyecto — obra a ejecutar. PK IdProyecto, FK IdCliente, Descripcion, Estado, FechaInicio, FechaFin, Ubicacion.
  • DetalleProyectoEmpleado — relación N:M entre proyecto y empleado con FechaIngresoEmpleado, ValorGanancia (sueldo aplicado al proyecto) y Estado.
  • DetalleProyectoMaterial — relación N:M entre proyecto y material con Cantidad, ValorGanancia y FechaIngresoMaterial.

Empleado, Material, Proveedor

  • Empleado — PK IdEmpleado, Nombre, Apellido, NroDocumento (int), Sueldo (float), CantidadProyectosActivos (denormalizado), IsActive.
  • Material — PK IdMaterial, DescripcionArticulo, TipoMaterial, TipoUnidad, CostoPorUnidad (float), FK IdProveedor.
  • Proveedor — PK IdProveedor, Descripcion, Telefono, IsActive.

Inventario, Material faltante y compras

  • Inventario — PK IdMaterialInventario, FK IdMaterial, Cantidad. Una fila por material en stock.
  • MaterialFaltante — materiales que un proyecto necesita pero no están en inventario. PK IdMaterialFaltante, FK IdProyecto, DescripcionArticuloFaltante, TipoMaterialFaltante, TipoUnidadMaterialFaltante, CantidadFaltante (int).
  • InformeDeCompra — agrupa materiales faltantes a comprar. PK IdInformeCompra, FK IdProyecto, FechaRealizacion, Estado (pendiente / finalizado / cancelado). Ver §13.
  • DetalleInformeMaterialFaltante — N:M entre informe y material faltante. PK IdDetalleMaterialFaltante, FKs IdInformeCompra, IdMaterialFaltante.
  • InformeMonto — agregados precomputados de un proyecto: TotalMateriales, TotalEmpleados, MontoTotal. Se recalcula con InformeMontoBL.Recalcular cada vez que se refresca el detalle del proyecto.

Dominio de Seguridad (DomainModel/Login/)

  • Usuario — IdUsuario (Guid), Mail, Contraseña (hash BCrypt), IsActive, Telefono, Idioma (es / en), Otp y OtpExpiry (recuperación), más una lista interna _permisos: IReadOnlyCollection<IPermiso>. Métodos AgregarPermiso(IPermiso) y TienePermiso(TipoPermiso).
  • Acceso — implementa IPermiso. Tiene Id (Guid), Nombre y DataKey (valor del enum TipoPermiso). Es el nodo hoja del árbol Composite.
  • Parametros — MargenEmpleados, MargenMateriales, UtilidadEmpresa (decimal 0..1), UltimaModificacion, ModificadoPor. Único registro, consumido por InformeMontoBL.
  • UserSession — DTO con datos cacheados de la sesión actual (Id, Mail, idioma, accesos).

7. Servicios transversales

7.1 Los catorce Business del BL

La capa BL tiene un servicio por entidad de negocio, todos siguiendo el mismo patrón UoW + try/catch + Log (ver §4.4). No son singletons: se instancian por uso. La lista exhaustiva:

ServicioResponsabilidad
ClienteBLCRUD de clientes.
ProveedorBLCRUD de proveedores.
EmpleadoBLCRUD de empleados, baja lógica con IsActive.
MaterialBLCRUD de materiales del catálogo.
InventarioBLAlta/baja de stock + CambiarCantidad. Las modificaciones de cantidad no generan log Info por ruido (ver §12).
ProyectoBLCRUD de proyectos.
ProyectoEmpleadoBL / ProyectoMaterialBLAsignación de empleados y materiales a un proyecto.
DetalleEmpleadoBL / DetalleMaterialBLManipulación del detalle (Detalle_proyecto_empleado, Detalle_proyecto_material).

DatabaseManagerInitializeDatabase() hace WarmUp de EF en Program.cs.

7.2 SessionManager — única fuente de verdad de la sesión

Singleton thread-safe en BL/LoginBL/SessionManager.cs. Tras un login exitoso, LoginService.TryLogin invoca SessionManager.Instance.Login(usuario) y a partir de ahí toda la UI consulta el usuario actual y sus permisos a través de la propiedad UsuarioActual y los helpers IsLoggedIn() / TienePermiso(TipoPermiso) / Logout(). Cerrar la app o llamar Logout libera la instancia.

7.3 LoggerLogic — fachada de bitácora

API estática en Services/Logs/LoggerLogic.cs. Internamente arma una única ILoggerStrategy vía LoggerFactory.Create() usando Lazy<T>. Niveles disponibles: Info, Warn, Debug, Error(msg, ex), Critical(msg, ex). Ver §12 para la convención de qué se loguea.

7.4 LanguageService — fachada de i18n

Singleton Services.Language.LanguageService.Current. Se inicializa una vez en Program.cs con un ResxLanguageRepository que lee las claves desde Properties/Resources.resx (default es-AR) y Resources.en-US.resx. La API se reduce a T(string clave) y SetCulture(string cultureCode). Ver §11.

7.5 PasswordHasher

Implementa IPasswordHasher en Services/LoginService/PasswordHasher.cs. Dos métodos:

  • Hash(plainText) — BCrypt.Net.BCrypt.HashPassword(plainText, workFactor: 12). Produce hashes con prefijo $2a$.
  • Verify(hash, plainText) — si el hash empieza con $2a$ / $2b$ / $2y$ usa BCrypt.Verify; si no, asume formato legacy SHA-256 en Base64 (usuarios anteriores a la migración a BCrypt) y compara hasheando el plain con SHA-256.

7.6 SnapshotService

Estático en Services/Historial/SnapshotService.cs. Persiste un archivo de texto por cada informe finalizado en %LOCALAPPDATA%\GestorCMB\historial\{idInforme}.txt con una línea por material faltante aplicado, en formato cantidad|descripcion|tipo|unidad. Permite reconstruir el historial incluso después de que los MaterialFaltante originales sean eliminados al aplicar la compra. Ver §13.

8. Flujos internos clave

8.1 Arranque de la aplicación

  1. Program.Main se suscribe a tres handlers de excepción no manejada (Application.ThreadException, AppDomain.UnhandledException, TaskScheduler.UnobservedTaskException) que delegan a HandleFatalException.
  2. Lee Properties.Settings.Default.CultureCode (default es-AR) y llama LanguageService.Initialize(new ResxLanguageRepository(), cultureCode).
  3. Lee la connection string ConnUsuarios. Si falta, muestra err_missing_cs_default y sale.
  4. Llama new DatabaseManager().InitializeDatabase() que internamente hace DatabaseService.WarmUp() (primer abrir-cerrar de EF para precargar el modelo).
  5. Construye AccessServicesFactory.CreateRolesService(cs) y new UsuarioService(cs) — esto crea el rol Administrador protegido si no existe y siembra los roles predefinidos (JefeDeObra, Operario, Comprador, Gerente).
  6. Application.Run(new LoginForm()).

8.2 Login

  1. LoginForm recibe mail + contraseña.
  2. Invoca LoginService.TryLogin(mail, pass, out Usuario u):
    • Si alguno está vacío → LoginResult.CredencialesInvalidas (no consulta la BD).
    • UsuarioRepository.FindByEmail(mail) sobre GestorCMB_Users.
    • Si IsActive == false → LoginResult.UsuarioInactivo (mensaje específico).
    • PasswordHasher.Verify(usuario.Contraseña, pass) — Ok o CredencialesInvalidas.
  3. Si Ok: se cargan los permisos heredados de los roles del usuario, se invoca SessionManager.Instance.Login(usuario) y LoggerLogic.Info(...).
  4. Se abre MainForm; los UserControl consultan SessionManager.Instance.TienePermiso(...) para mostrar u ocultar sus acciones.

8.3 Recuperación de contraseña (OTP por mail)

  1. Usuario abre ForgotPasswordForm e ingresa su mail.
  2. OtpService.EnviarOtp(mail) busca el usuario activo, genera un entero entre 100000 y 999999, calcula OtpExpiry = DateTime.Now + 15min, persiste ambos campos en el Usuario y envía un correo SMTP con asunto "Código de recuperación de contraseña".
  3. El usuario recibe el código, lo ingresa junto con la nueva contraseña.
  4. OtpService.ValidarOtp(mail, otp) compara con StringComparison.Ordinal (tras Trim()) y chequea expiración.
  5. Si es válido, OtpService.CambiarContraseña(mail, nueva) hashea con PasswordHasher.Hash y limpia Otp/OtpExpiry.
Privacidad. Si el mail no corresponde a un usuario activo, el servicio devuelve false sin lanzar excepción. La UI muestra un mensaje genérico para no filtrar la existencia de cuentas.

8.4 Operación CRUD con Unit of Work (canónico)

Ver §4.4. Todo método Add/Update/Delete en un BL sigue:

  1. Validación de argumentos → throw new AppException("clave").
  2. using (var ctx = new GestorCMBEntities()) + using (var uow = new SqlUnitOfWork(ctx)).
  3. uow.Begin().
  4. try { repo.X(entity); uow.Commit(); LoggerLogic.Info(...); }.
  5. catch (AppException ex) { uow.Rollback(); LoggerLogic.Warn(ex.MessageKey); throw; }.
  6. catch (Exception ex) { uow.Rollback(); LoggerLogic.Error(contexto, ex); throw; }.

Los métodos de consulta (GetAll, GetById, FindBy*) no abren transacción, no envuelven en try/catch y no loguean. Las excepciones burbujean al Form que las captura.

8.5 Generar y aplicar un informe de compra

Detalle completo en §13. Resumen del flujo "aplicar compra" (ConfirmarCompraYAplicar):

  1. Obtiene los MaterialFaltante del informe.
  2. Para cada uno, busca el Material del catálogo por descripción + tipo + unidad (case-insensitive, trim).
  3. Si lo encuentra: incrementa o crea el DetalleProyectoMaterial del proyecto con fecha del día.
  4. SnapshotService.Guardar(idInforme, faltantes).
  5. Borra los DetalleInformeMaterialFaltante que apuntan a esos faltantes.
  6. Marca el informe actual como finalizado y cualquier otro informe pendiente del mismo proyecto como cancelado.
  7. Elimina los MaterialFaltante del proyecto.
  8. Todo dentro de un único SqlUnitOfWork — si algo falla, Rollback.

8.6 Cambio de idioma en runtime

  1. Usuario edita su perfil en EditUserForm y selecciona idioma (es / en).
  2. UsuarioService.Update persiste el cambio en GestorCMB_Users.
  3. Si el usuario editado es el logueado, la UI guarda Properties.Settings.Default.CultureCode = "es-AR" | "en-US" y llama Application.Restart(). Los Forms Localizable reciben la cultura nueva; los no-Localizable ejecutan su AplicarTraducciones() en el constructor. Ver §11.

8.7 Manejo de excepciones globales

Los tres handlers de Program.Main delegan a HandleFatalException, que:

  1. Llama LogHelper.Error("Excepción no controlada", ex).
  2. Si ex is AppException → muestra T(appEx.MessageKey).
  3. Si no, muestra T("err_generic").
  4. Sugiere abrir VerLogsForm para más detalle.

9.5 Hash de contraseñas

  • Default actual: BCrypt con work factor 12. El hash incluye salt aleatorio único; dos contraseñas iguales producen hashes distintos. Comprobación con BCrypt.Verify.
  • Legacy aceptado: SHA-256 en Base64 sin prefijo. Pensado para usuarios anteriores a la migración. No hay rehash al loguear (los hashes legacy permanecen hasta el próximo cambio de contraseña).

9.6 Deuda técnica conocida del esquema

  • Nombres de columnas en español + camelCase mezclados (idProyecto, fechaRealizacion, descripcionArticulo). EF mapea por Code a propiedades PascalCase del lado .NET.
  • telefono en Cliente y otras tablas es int: no soporta prefijos internacionales ni el dígito cero inicial.
  • La BD de seguridad convive con un nombre legacy CMB_USERS en una connection string; la efectiva es GestorCMB_Users (usada por ConnUsuarios).
  • No hay scripts SQL versionados todavía: la creación de las tres bases se hace a mano contra una instancia local.
  • Empleado.cantidadProyectosActivos es un campo denormalizado; mantener sincronizado al asignar/desasignar empleados.

10. Seguridad y permisos

10.1 Modelo Composite

Los permisos forman un árbol con dos tipos de nodos:

  • Acceso (hoja) — implementa IPermiso; tiene un DataKey que es un valor del enum TipoPermiso. Su TienePermiso(p) retorna DataKey == p.
  • RolCompuesto (compuesto) — implementa IPermiso; mantiene una lista interna de hijos. Su TienePermiso(p) recorre recursivamente la lista.

Al loguear, los servicios del módulo de seguridad cargan los roles del usuario, arman su RolCompuesto con todos sus Acceso hijos, y lo inyectan en Usuario._permisos. La UI consulta SessionManager.Instance.TienePermiso(TipoPermiso.X) antes de renderizar cada acción.

10.2 Roles predefinidos (seed)

RolesService mantiene cinco GUIDs constantes y crea/repara estos roles en el arranque si no existen:

  • Administrador — protegido (sólo lectura desde la UI). Tiene todos los permisos.
  • JefeDeObra — gestión de proyectos, empleados, materiales y compras de su obra.
  • Operario — visualización del proyecto en el que está asignado.
  • Comprador — gestión de informes de compra e inventario.
  • Gerente — visualización amplia + configuración de parámetros.
Last-admin guard. El rol Administrador es protegido en la UI: la matriz de toggles aparece deshabilitada y RolesService impide modificar o eliminar sus permisos. Esto evita que un administrador se autoexpulse del sistema por error.

10.3 TipoPermiso — los 15 permisos del sistema

11. Internacionalización

La app es bilingüe es-AR / en-US. La traducción se hace 100% por clave contra Properties/Resources.resx (ES, default) y Properties/Resources.en-US.resx (EN). El acceso runtime es LanguageService.Current?.T("clave").

11.1 Cómo se traduce en runtime

  1. Program.Main lee Properties.Settings.Default.CultureCode.
  2. Instancia ResxLanguageRepository (en MatheoCaffieri_GestorCMB/Localization/) y llama LanguageService.Initialize(repo, cultureCode).
  3. LanguageService.SetCulture asigna tanto Thread.CurrentThread.CurrentCulture como CurrentUICulture.
  4. Cada vez que el código necesita una cadena: LanguageService.Current?.T("clave") ?? "fallback en español". El fallback se ejecuta sólo si el servicio no se inicializó (defensivo).
  5. Para mensajes con argumentos: string.Format(T("clave_fmt"), arg0, arg1). Convención: nombrar la clave con sufijo _fmt.

11.2 Convención de nombres de claves

PrefijoUso

11.3 Dos mecanismos de traducción por Form

Hay dos maneras de gestionar i18n en WinForms y conviven en GestorCMB porque algunos Forms se construyeron con Localizable=true en el Designer (VS migra automáticamente los .Text = "..." a resources.ApplyResources(...) y crea el .en-US.resx del Form) y otros no.

  • Forms Localizable=true: tienen su propio .en-US.resx auto-generado. Los Text de cada control se traducen automáticamente al cambiar Thread.CurrentThread.CurrentUICulture. Incluyen, entre otros: MainForm, AddEmpleadosForm, AddMaterialesForm, AddProyectosForm, AccesosForm, EditUserForm, ClientesControl, ProveedorControl, VerEmpleadosControl, VerProyectosControl, VerInventarioControl, DetalleProyectoControl, GestionUsuariosControl, InformesDeCompraControl, HomeControl, ConfigurarParametrosControl y varios ItemControls.
  • Forms no-Localizable: tienen textos hardcoded en el Designer y no tienen .en-US.resx propio. Implementan un método privado AplicarTraducciones() que se llama en el constructor (después de InitializeComponent()) y sobreescribe los .Text con LanguageService.Current?.T(...). Aplican a LoginForm, EditEmpleadoForm, VerLogsForm, ForgotPasswordForm (este construye su UI programáticamente con T() inline) y los 3 Header controls (DetalleEmpleadoHeaderControl, DetalleMaterialHeaderControl, MaterialFaltanteHeaderControl).

11.4 Cómo agregar un idioma

  1. Crear Properties/Resources.{cultureCode}.resx (p. ej. Resources.pt-BR.resx) con las mismas claves que Resources.resx.
  2. Para los Forms Localizable=true: abrir cada Form en el Designer con la cultura nueva activa y traducir los Text de cada control. VS genera el .{cultureCode}.resx del Form.
  3. Para los Forms no-Localizable: nada que hacer si AplicarTraducciones() ya usa T() para todos los strings.
  4. Actualizar el combo de idiomas en EditUserForm y persistir el código.

12. Bitácora y logging

12.1 Estrategias y configuración

LoggerFactory.Create() lee la clave LoggerType de App.config y arma la ILoggerStrategy resultante:

ValorEstrategia armada
file (default)FileLoggerStrategy
databaseDatabaseLoggerStrategy
both o "file,database"CompositeLoggerStrategy(file, database)

Otras claves de App.config relevantes:

  • LogDirectory — carpeta de archivos. Default logs (relativo al ejecutable). En el repo está en C:\Logs\MiApp.
  • LogRetentionDays — días de retención de archivos. Default 14.

12.2 FileLoggerStrategy

Crea un archivo por día y por nivel: yyyyMMdd_info.log y yyyyMMdd_error.log en LogDirectory. Modo append, encoding UTF-8. Formato: 

[2026-05-26 10:14:33] [INFO]  :: [ProyectoBL] Proyecto agregado. Id=ab12-... Desc='Obra Centro'
                                    | date=2026-05-26 10:14:33
[2026-05-26 10:14:40] [ERROR] :: [ProyectoBL] Falla al agregar proyecto. Id=...
                                    | date=2026-05-26 10:14:40
                                    | ex=System.Data.Entity.... at ProyectoRepository.Add...

Al inicio de cada escritura, TryRetention(dir) borra archivos cuya fecha de modificación supere LogRetentionDays.

12.3 DatabaseLoggerStrategy

LoggerRepository.WriteLogToDatabase() abre una SqlConnection contra LogsConnection e inserta en la tabla Log (Fecha, Nivel, Mensaje, Excepcion). La UI de VerLogsForm lee de esa tabla.

12.4 CompositeLoggerStrategy

sealed, recibe params ILoggerStrategy[] targets. Reenvía WriteLog a cada hijo dentro de un try/catch individual: si un sink falla (p. ej. BD caída), los demás siguen funcionando.

12.5 Convención: qué se loguea y qué no

LoggerLogic es la única forma de loguear. En la UI VerLogsForm los niveles se ven así: Warn = naranja (validaciones), Error / Critical = rojo (fallas reales), Info = neutro (eventos de éxito).

Qué SÍ se loguea

  • Login: Info en éxito, Warn en credenciales inválidas o usuario inactivo (BL.LoginBL.LoginService.TryLogin).
  • Creación, modificación y eliminación de entidades: un solo log Info por operación, en el BL después del Commit. Formato: "[XxxBL] <Entidad> <verbo>. Id={...}".
  • Validaciones de UI (campo vacío, dato inválido, dato duplicado): LoggerLogic.Warn ANTES del MessageBox.Show. Formato: "[XxxForm] Validación: <qué falla>.".
  • Validaciones de negocio (catch (AppException ex)): LoggerLogic.Warn con el MessageKey.
  • Fallas de sistema (catch (Exception ex)): LoggerLogic.Error("contexto", ex) con la excepción.

Qué NO se loguea

  • Consultas: GetAll, GetById, Exists, FindBy*. Sin try/catch en el BL; dejar que la excepción burbujee.
  • Búsquedas por barra de filtro.
  • Navegación entre Forms / Controls.
  • Cambios de cantidad de inventario: InventarioBL.Update y InventarioBL.CambiarCantidad no loguean éxito (sí loguean error). InventarioBL.Add / Delete sí loguean.
  • InformeMontoBL.Recalcular: no loguea éxito (se llama en cada refresh).
  • Logs duplicados entre BL y DAL: el log vive en el BL después del Commit; los repos EF no loguean.

13. Historial de informes de compra

Un InformeDeCompra atraviesa tres estados que conviven en la misma tabla Informe_compra mediante la columna estado (varchar(20) NOT NULL DEFAULT 'pendiente'):

EstadoSignificadoDetalles en BD
pendienteRecién generado, aguarda confirmación de compra.Se conservan los DetalleInformeMaterialFaltante.
finalizadoLa compra fue aplicada al proyecto.Se borran los detalles y los MaterialFaltante; se guarda snapshot en archivo (ver abajo).
canceladoEl informe fue descartado sin aplicarse.Los detalles se conservan; los faltantes del proyecto siguen disponibles.

13.1 Comportamiento del repositorio

  • InformeDeCompraRepository.GetAll() retorna solo los pendiente. Es lo que muestra InformesDeCompraControl.
  • GetHistorial() retorna finalizado + cancelado. Es lo que muestra HistorialInformesControl.
  • InformeDeCompraBL.EliminarInforme → estado = 'cancelado' (no DELETE físico).
  • InformeDeCompraBL.ConfirmarCompraYAplicar → estado = 'finalizado' + borra detalles y faltantes + persiste snapshot.

13.2 Snapshot persistido en disco

Al pasar a finalizado, se borran los MaterialFaltante y sus detalles. Para conservar la trazabilidad, SnapshotService.Guardar(idInforme, faltantes) escribe un archivo de texto en: 

%LOCALAPPDATA%\GestorCMB\historial\{idInforme:N}.txt

cantidad|descripcion|tipo|unidad
cantidad|descripcion|tipo|unidad
...

SnapshotService.Leer(idInforme) reconstruye la lista al mostrar el historial. Si el archivo no existe (por ejemplo, en otra máquina o si se borró el perfil de usuario local), el ítem se muestra sin materiales — el sistema no aborta la carga del resto.

13.3 Migración SQL

Para entornos pre-existentes, agregar la columna: 

ALTER TABLE Informe_compra
ADD estado varchar(20) NOT NULL DEFAULT 'pendiente';

13.4 UI

  • InformesDeCompraControl: lista de pendientes agrupados por proyecto. Botón "Historial" navega a HistorialInformesControl.
  • HistorialInformesControl: lista del historial filtrable por descripción del proyecto o razón social del cliente. Acción única es la búsqueda — no se permite editar ni reabrir.

14. Reglas de negocio principales

14.1 Usuarios y roles

  • Un usuario puede pertenecer a uno o más roles y hereda todos sus permisos.
  • El rol Administrador tiene siempre todos los permisos y no es editable desde la UI.
  • UsuarioPermisosService.ReemplazarDirectos permite asignar accesos directos a un usuario sin que dependa de un rol.
  • Mail único por usuario; el sistema rechaza duplicados con err_usuario_mail_duplicado.
  • Baja lógica con IsActive=false: la sesión no abre y el OTP no se envía.

14.2 Recuperación de contraseña

  • OTP de 6 dígitos.
  • Expiración 15 minutos desde la generación.
  • El OTP se invalida solo después de aplicar el cambio de contraseña exitosamente (permite reintentos).
  • Si el mail no corresponde a un usuario activo, el servicio devuelve false sin enviar correo ni filtrar la existencia de la cuenta.

14.3 Proyectos

  • Un proyecto pertenece a un único cliente.
  • Asignar un empleado a un proyecto incrementa Empleado.CantidadProyectosActivos; quitarlo lo decrementa.
  • El monto total del proyecto se calcula con InformeMontoBL.Recalcular(idProyecto): totalEmpleados × (1 + MargenEmpleados) + totalMateriales × (1 + MargenMateriales) + UtilidadEmpresa. Los parámetros se editan en ConfigurarParametrosControl.

14.4 Materiales e inventario

  • Un material pertenece a un proveedor.
  • El inventario tiene una fila por material; la columna cantidad es int (no soporta fracciones).
  • El cruce material-faltante ↔ material del catálogo se hace por descripción + tipo + unidad, case-insensitive y con Trim.

14.5 Informes de compra

  • Solo se puede generar un informe por proyecto por día (unicoPorDia=true): si ya existe uno hoy, se reutiliza y se agregan los faltantes que no estaban.
  • Generar requiere GESTIONAR_INFORMES_COMPRA y al menos un faltante; consultar requiere VER_INFORMES_COMPRA.
  • Aplicar un informe cancela automáticamente los demás informes pendiente del mismo proyecto.
  • Cancelar un informe es soft-delete (estado a cancelado); no borra el registro físico.

14.6 Parámetros del sistema

  • MargenEmpleados, MargenMateriales y UtilidadEmpresa se almacenan como decimal entre 0 y 1; en la UI se ingresan como porcentaje (multiplicado por 100).
  • Cada guardado actualiza UltimaModificacion y ModificadoPor.
  • Requiere permiso CONFIGURAR_PARAMETROS.

15. Cómo extender el sistema

15.1 Agregar un campo a una tabla de GestorCMB

  1. Modificar la tabla en SQL (script ALTER TABLE).
  2. Abrir DAL/GestorCMBEntityModel.edmx:
    • Agregar la columna en el SSDL (storage).
    • Agregar la propiedad en el CSDL (conceptual).
    • Mapearla en el MSL (mapping).
  3. Editar el archivo .cs auto-generado de la entidad EF en DAL/ (agregar la propiedad pública).
  4. Reflejar el campo en la entidad de dominio correspondiente (DomainModel/Entities/).
  5. Actualizar el repositorio EF (DAL/ProjectRepo/) — generalmente solo afecta a las consultas que materializan la entidad.
  6. Si requiere lógica, agregar la regla al BL y, en caso de validación de UI, agregar la clave a Resources.resx y Resources.en-US.resx.

15.2 Agregar un permiso nuevo

  1. Agregar el valor al enum TipoPermiso en Interfaces/LoginInterfaces/TipoPermiso.cs.
  2. Crear el Acceso en la BD GestorCMB_Users (tabla Acceso) con dataKey igual al nombre del enum, o usar AccesoService.CrearAcceso(nombre, TipoPermiso) desde AccesosForm.
  3. Asignar el permiso al rol Administrador en RolesService.EnsureAdminExists para que quede semilla.
  4. En la UI, consultar SessionManager.Instance.TienePermiso(TipoPermiso.X) antes de mostrar la acción.

15.3 Agregar un rol predefinido

  1. Definir un Guid constante en RolesService (siguiendo el patrón de AdminRoleId).
  2. Agregarlo a EnsureRolesPredefinidosExist con su set inicial de accesos.

15.4 Agregar un módulo / pantalla completa

  1. Crear el UserControl en MatheoCaffieri_GestorCMB/. Preferentemente con Localizable=true en el Designer para evitar tener que escribir AplicarTraducciones().
  2. Registrarlo en MainForm (panel de navegación + lógica de carga).
  3. Si el módulo persiste datos: agregar entidad en DomainModel, interfaz en DomainModel/Interfaces/, repo EF en DAL/ProjectRepo/, BL en BL/ (siguiendo el patrón de §4.4).
  4. Definir un permiso VER_X y GESTIONAR_X en TipoPermiso y aplicar guardas.
  5. Agregar todas las claves de i18n a ambos .resx.

15.5 Agregar un sink de logging

  1. Implementar ILoggerStrategy en Services/Logs/Strategy/.
  2. Agregar el caso en LoggerFactory.Create() (mapeo del valor de LoggerType).
  3. Si se quiere combinar con otros, LoggerType=both ya soporta lista por comas a través de CompositeLoggerStrategy.

15.6 Agregar un idioma

Ver §11.4.

BCryptAlgoritmo de hash unidireccional usado para guardar contraseñas. Work factor 12 (~250 ms por hash).
BLBusiness Logic. Capa que orquesta repositorios y aplica reglas de negocio.

Cultura / CultureCodees-AR o en-US. Persistido en Properties.Settings.Default.CultureCode.

InformeDeCompraAgrupación de materiales faltantes de un proyecto pendientes de comprar. Tres estados: pendiente / finalizado / cancelado.
InformeMontoAgregado precomputado del monto total de un proyecto, recalculado en cada refresh.
MaterialFaltanteMaterial que un proyecto necesita pero no está cubierto por el inventario.

ParametrosConfiguración global: márgenes de empleados, márgenes de materiales y utilidad de la empresa. Una sola fila en BD.
RolCompuestoNodo compuesto del árbol de permisos. Agrupa Accesos y otros RolCompuestos. Implementa IPermiso (Composite pattern).
SessionManagerSingleton de sesión. Mantiene el Usuario autenticado y expone TienePermiso a la UI.
SHA-256 legacyFormato de hash usado por versiones previas del sistema, aceptado por compatibilidad retroactiva en PasswordHasher.Verify.

TipoPermisoEnum con los 15 permisos del sistema (VER_* y GESTIONAR_*).
